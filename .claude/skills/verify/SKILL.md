# GLATasksの実行時検証

GLATasksはブラウザーのWeb/PWA画面から操作する。HTTPの疎通は内部ネットワークから補助的に確認する。
この手順ではMCPや、外部サービスを使う機能を検証しない。

## 起動と状態確認

1. Linuxの**主作業ツリー**で、対象変更を含むcommitに揃え、`git status --short`が空であることを確認する。
   別worktreeの未統合変更や稼働中の開発環境は対象外。開発セットアップの前提は[開発手順](../../../docs/development/development.md)を参照する。
   実行中はチェックアウトやソースの編集をしない。
2. `docker compose ps`で通常の開発環境のコンテナーID・状態を控える（停止中なら起動しない）。
   機能を1つ選び、「実行コマンド」のとおりに起動する。
3. 補助スクリプトは`make test-e2e`を呼ぶ。`flock .cache/test-e2e.lock`で排他を取り、
   `*-e2e`プロジェクト内で空のMariaDBと専用の`E2E_DATA_DIR`を使う。
   `test-e2e-isolated`は直接呼ばない。
   起動・マイグレーション・疎通の後、ロック中の読取専用確認でプロジェクト、公開ポートなし、
   DBのtmpfs、アプリのソースとデータのマウント、コンテナー内のcommit、空DBを確かめる。
   対象版は、主作業ツリーをマウントして起動した開発サーバーのソース版である。
   条件を満たさなければ操作せず終了する。
4. PlaywrightはComposeネットワークの`https://web`を使う。
   既存のグローバルセットアップが試験ユーザーを登録し、選んだ1機能の手順を公開画面から実行する。
   ホストから既存の公開ポートへ接続しない。

## 実行コマンド

タスク編集の例。未使用の証拠ディレクトリ名を渡す。

```bash
.claude/skills/verify/run.sh "$(git rev-parse HEAD)" "$PWD/.cache/verify-01" task-edit
```

## 操作と観測

| 引数          | 操作                                                                                      | 確認する証拠・注意点                                                                          |
| ------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `task-create` | `/`で試験用リストを選び、`task-add-form`の入力欄から作成する                              | `task-item`の新規表示と、Trace Viewerで作成の応答を確認する。楽観表示だけでは保存成功としない |
| `task-edit`   | 同画面で作成した行の保存を待ち、`task-edit-btn`から変更して`task-edit-save-btn`で保存する | `tasks.update`の応答と編集した文字列の表示を確認する                                          |
| `timer`       | `/timers`で1分のタイマーを作成し、`timer-start-btn`で開始して`timer-pause-btn`で止める    | 58秒以下まで進んだ表示と再開ボタンを確認する。満了・通知はこの操作の対象外                    |
| `auth`        | 未ログインの`/`からログイン画面に進み、試験用の資格情報でログインする                     | ログイン応答と`/`への遷移を確認する。実ユーザーの資格情報を使わない                           |

操作は既存の`app/tests/{tasks,timers,auth}.test.ts`の該当ケースを再利用する。画面、API、保存状態の証拠は次のように区別する。

- 証拠ディレクトリの`playwright/`内の`trace.zip`を`pnpm --dir app exec playwright show-trace <trace.zipの絶対パス>`でローカルに開く。
  スナップショットとNetworkを見比べ、画面と該当応答を確認する。HTTP成功だけでtRPCの成功とせず、エラーの有無も見る。
- `run.log`には対象commit、コンテナーID、ヘルスチェック応答の状態コード、操作前後のDB件数、コンテナーログが残る。
  DB件数は空DBから始まったことと終了時の状態の傍証であり、個々の操作の保存内容を示すものではない。
  タスクの試験用リストやタイマーはケース自体が回収する。
- エラーは`run.log`と、Makeが保存した場合は`failure.log`を確認する。
  証拠に試験用のセッション情報が含まれ得るため、共有・commitせず、報告には観測結果だけを抜き出す。

## 後始末

Makeがロックを保持したまま対象プロジェクトを`down --volumes --remove-orphans`し、専用データディレクトリを除去する。
終了コードと`run.log`の「残留コンテナー: なし」、証拠が残っていることを確認し、通常の`docker compose ps`を控えと比較する。
途中で強制終了して回収が確認できなければ、同じ主作業ツリーから通常の手順を新しい証拠ディレクトリで再実行する。
`make test-e2e`が排他内で前回の試験資源を回収する。開発プロジェクトを止めて回収しない。
